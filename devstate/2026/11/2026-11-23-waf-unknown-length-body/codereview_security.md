# Security

1. [judgement] Fail-open on deny — `pkg/appsec/client.go:61` — an operator who set `appsecBodyLimit: 0` to have AppSec see the whole body now gets the 10 MiB cap with no runtime signal, so a client that pads a POST/PUT/PATCH/DELETE body past 10 MiB gets its tail to origin uninspected (`TruncateAtLimit`, `pkg/appsec/query.go:149`). Source is the client body; reach depends on that operator config. The cap itself is the approved BREAKING decision (design.md risk row "without being told"; upgrade note in `docs/configuration.md`), so not hard
   Fix: Log one WARN at `Prepare`/`New` when the configured `appsecBodyLimit` is 0 or negative, naming the effective 10485760 cap and that bytes past it reach origin uninspected
   Status: skipped
   Argument: Judgement: the 10 MiB cap for `appsecBodyLimit <= 0` is the approved breaking decision, documented in the `docs/configuration.md` upgrade note and the card's Operators line; a startup WARN is new behaviour beyond the ask.
2. [judgement] Client-controlled trust — `pkg/wafhop/body.go:155` — when `ctrl.SetReadDeadline` fails (writer chain without `Unwrap`, e.g. a Traefik older than v3.7.17 per the research note), the fallback `body.Close()` cannot cut an HTTP/1.1 chunked read (Close waits on the body mutex), so a stalled chunked body is held until Traefik's entry point `readTimeout` (none if the operator set 0) instead of the leg's timeout, and nothing records that the configured bound did not apply. Still fails closed (400 once the read returns) and is no worse than master, which read HTTP/1.1 chunked bodies with no deadline at all
   Fix: When `SetReadDeadline` returns an error on a request with `ProtoMajor == 1`, log a debounced WARN that the body read timeout cannot be enforced on this Traefik writer chain
   Status: skipped
   Argument: Judgement: no regression versus master (HTTP/1.1 chunked had no plugin deadline at all) and the request is still answered 400; a new WARN surface is beyond the ask. Not applied unattended.
3. [hard] Client-sized allocation at the uncapped limit (regression; hard because both configs are accepted, with the operator precondition stated here) — `pkg/wafhop/body.go:120` — `buf.Grow(int(httpReq.ContentLength))` now runs whenever `0 < ContentLength <= limit`, outside the `limit < math.MaxInt64` branch. In the base (`.pin_diff/base/pkg/wafhop/body.go:116-121`) Grow ran only under `limit > 0 && limit < math.MaxInt64`, so at `math.MaxInt64` the buffer grew only as bytes arrived. Source: the client's `Content-Length` header (HTTP/1.1 or HTTP/2, any value up to MaxInt64), on a POST/PUT/PATCH/DELETE for AppSec or any method with a body for ModSec. Sink: one upfront allocation of that size before any body byte is read. Precondition: the operator sets `appsecBodyLimit` or `modsecBodyLimit` to 9223372036854775807. Validation accepts both (AppSec has no range check, ModSec checks only `>= 1`). That value is the one `ReadBody` handles as "read the whole body" (`TestReadBody_maxInt64LimitReadsAll`), and it is the obvious choice for an operator who reads the upgrade note that `0` no longer means unlimited. Blast radius: one request with no body bytes forces a multi-GB or TB allocation. Inference, not measured: a size the OS refuses is a fatal Go runtime `out of memory` throw, not a recoverable panic, so the whole Traefik process stops; a size the OS grants pins that memory per request. For any huge finite limit below MaxInt64 the base already allowed the same Grow, so the regression is only the MaxInt64 value
   Fix: Move the Grow back under the `limit < math.MaxInt64` branch
   Status: done
   Argument: Moved `buf.Grow` back under the `limit < math.MaxInt64` branch in `pkg/wafhop/body.go`; added `TestReadBody_maxInt64LimitIgnoresDeclaredLength` (a huge declared Content-Length at the uncapped limit reads the real body without a client-sized allocation).
