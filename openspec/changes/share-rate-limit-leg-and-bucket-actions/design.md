## Context

See proposal.md for why. Measured on this branch (head `7173cac5`, round 1 archived as `2026-11-21-add-redis-rate-limit-leg`; dest `master`):

- `plugin.go` wires LAPI, AppSec, captcha, and ModSec by hand: four `Prepare` calls in `New`, a `switch group` arm per leg in `openOwnedLeg` and `claimOwnedLeg`, a hand-written rollback list per claim in `claimOwned` / `clearClaimedPublishers`, four `subscribe*` booleans and four `reclaim.Watch` calls in `New`. The rate-limit leg sits beside them as `openRateLimit` + `AttachRateLimit` (no alias, no Watch, no `ClearPublisher`).
- `pkg/bouncer`: per leg a `<leg>Bound atomic.Value`, `subscribe<Leg>`, `<leg>Received`, `<leg>ReceiveSeen`, `<leg>InstanceName` on `Bouncer`, and an identical `loaded<Leg>` / `Receive<Leg>` / `receive<Leg>` trio in `bouncer_leg_{lapi,appsec,captcha,modsec}.go` (LAPI adds the stream-scope warning and `LapiClient` / `SameLapiClient`). `bouncer.New(next, name, config, subscribeLAPI, subscribeAppSec, subscribeCaptcha, subscribeModsec, log)` has 15 call sites.
- `pkg/configuration` imports `pkg/ratelimit` (`Config.RateLimitBuckets []ratelimit.BucketRule`), so `pkg/ratelimit` cannot take a `*configuration.Config`.
- `reclaim.SetAlias(key, alias, publisher, group)` clears the publisher's other aliases in the same group (vendored `reclaim/alias.go`), so a renamed instance moves without extra code; a closed incarnation clears its aliases for subscribers.
- Yaegi v0.16.1 (CI pin), measured in explore: a generic type named through a package qualifier panics; a binding whose received field is an interface or `any` fails at runtime; a non-generic binding that keeps the traced incarnation as a `string` plus a table of plain structs with func fields passes under Yaegi and Go.
- `logger.Debounced(log, level, interval, msg, …)` keys its window on `msg`, process-wide.
- `captcha.Client` already offers `Check(req)` (gate cookie), `IsCustomResourceRequest(r)` (custom-provider widget assets), `HasChallengeMarker(r)`; `Bouncer.usableCaptcha()` is the "subscribed, published, valid" owner.

## Goals / Non-Goals

**Goals:**

- The four published legs live on one descriptor table and one binding type before the rate-limit leg changes, in a commit whose tests prove nothing observable moved.
- The rate-limit leg becomes the fifth descriptor with no per-leg copy outside its own Client, receive hook, and request step.
- Every captcha answer of the rate-limit leg is decided on the subscribing router, at request time, without a startup failure and without per-request WARN/ERROR.

**Non-Goals:**

- Renaming leg / instance / backend vocabulary (`knowledge/debt/2026-09-23-leg-instance-backend-vocabulary.md`).
- Any change to LAPI, AppSec, captcha, or ModSec behaviour, including the pre-existing per-request WARN on their unsubscribed captcha path.
- Single-EVAL Redis design, Redis TLS / ACL, `RateLimit-*` headers, per-subscriber overrides, a subscriber-side rate-limit failure action.

## Decisions

1. **One OpenSpec change, refactor first in `tasks.md`.** The leg extraction has no live promise of its own (Live catalog: behaviour-preserving refactor → no spec delta), so a separate change would be spec-less, and `handoff.yaml` carries one `change:` per run. The human asked for one PR whose first commit is the behaviour-preserving extraction; task group 1 is exactly that commit, with its own verification, and nothing in it reads a rate-limit symbol. Alternative: two changes (`extract-leg-descriptor`, then this one) — rejected for the reasons above.

2. **Descriptor table in `plugin.go`.** One unexported struct type, one value per leg, in a fixed slice: LAPI, AppSec, captcha, ModSec (group 1), then the rate limit (group 2). Fields are plain values and funcs: `group string`, `enabled func(*configuration.Config) bool`, `instanceName func(*configuration.Config) string`, `prepare func(*configuration.Config, *slog.Logger, string) error`, `open func(ctx, *configuration.Config, *slog.Logger, name string) error`, `ownershipKey func(*configuration.Config, string) string` (AppSec assigns `appsec.Key`, no rename), `empty any` (typed nil for `Watch`), `receive func(*bouncer.Bouncer) func(any)`. `New` iterates it for prepare, open (`ClearPublisher` when not enabled), claim, subscription, and Watch. Claim rollback: a failed claim calls `ClearPublisher` on every earlier entry that is enabled — the same lists as today (AppSec → LAPI; captcha → LAPI, AppSec; ModSec → LAPI, AppSec, captcha). No generics (Yaegi). Alternatives: generic descriptor / binding — rejected (Yaegi panic, measured); keeping the switches and adding a fifth arm — rejected by B-4.

3. **One binding type on `Bouncer`, one subscription value into `bouncer.New`.** A non-generic `legBinding` (bound `atomic.Value` holding `*reclaim.Box`, `subscribed bool`, `leg`, `instanceName`, last traced incarnation `string`, seen flag) replaces the five per-leg field groups; `bindingMu` stays one mutex. Each leg keeps a typed one-line `loaded<Leg>()` and an exported `Receive<Leg>(published any)` (plugin.go needs a typed callback for `Watch`), both delegating to one `receiveBinding` that stores the new Box and traces bound / unbound exactly as today (same messages, attrs, and conditions; the previous incarnation comes from the stored string instead of the previous pointer). Per-leg extras stay as a bind hook: LAPI's stream-scope warning, the rate limit's captcha check (decision 9). The rate limit also passes an unbind hook (decision 9, owner loss); the other legs pass nil. `bouncer.New(next, name, config, subscriptions Subscriptions, log)` with `Subscriptions{LAPI, AppSec, Captcha, ModSec bool}` in group 1 and `RateLimit` added in group 2 — one named value for facts that travel together, so the fifth leg adds a field, not a sixth parameter at 15 call sites. Alternative: keep four booleans and add a fifth — rejected (15 more edits and a sixth positional bool).

4. **Rate-limit descriptor.** `prepare`: fill an omitted `rateLimitInstanceName` with the Traefik name when `rateLimitEnabled`; it lives in `plugin.go`, not `pkg/ratelimit`, because of the import cycle above. `open`: the existing `openRateLimit` path (password via `GetVariable`, sync rate via `RateLimitSyncRateDuration`) builds `ratelimit.Settings` — the Redis settings plus `Buckets []BucketRule`, `FailureAction` (via `EffectiveRateLimitFailureAction`), `StatusCode`, `ResponseHeaders`, and `InstanceName` (logs only) — and calls `ratelimit.Open(ctx, name, settings, log)`. `ownershipKey`: `ratelimit.OwnershipKey(name, settings)` hashing everything except `InstanceName`. Claim runs last, so a rate-limit claim failure clears the four other enabled legs; the leg gains `ClearPublisher` when its flag drops. `openRateLimit`'s position before `claimOwned` and `AttachRateLimit` go away.

5. **The published `ratelimit.Client` carries its policy.** `Open` compiles `NewBucketSet` once in the reclaim `create` and stores it with the policy on the Client; accessors return the bucket set and the policy; a nil-safe `Incarnation()` matches the other four Clients; lifecycle lines gain `instanceName`. `Bouncer` drops `rateLimitBuckets`, `rateLimitCounter`, `rateLimitFailureAction`, `rateLimitStatusCode`, `rateLimitResponseHeaders`, and `AttachRateLimit`; `serveRateLimit` loads the Client per request and reads them from it. The `Counter` interface stays for `Charge` and test fakes. Alternatives: publish only the Redis counter and compile buckets per subscriber — rejected (B-2); republish a changed policy on the same Client — rejected (mutates a value live requests read; no precedent).

6. **Request step order in `serveRateLimit`.** (a) no loaded Client or `SkipRateLimit` → continue; (b) the router has a usable captcha and the request is a custom widget asset → continue, nothing charged; (b') the router has a usable captcha, the policy can answer with a captcha (a `captcha` bucket or failure action `captcha`), no `bypassCaptcha` rule matched, and the request carries the challenge marker (`isRateLimitChallengeFormAnswer`, checked in that order so the body is read last) → nothing charged, and `handleCaptchaKindServeHTTP(rw, req, ReasonRateLimit, headerReasonRateLimit, lapi.OriginPluginRateLimitChallengeForm)` answers it (valid answer → 302 `captcha:solved` with the gate cookie; otherwise the challenge page again, header `captcha:ratelimit`, drop `captcha` under origin `plugin:ratelimit`); any other marker POST goes on to (c) and is charged like any request. Amended after round-2 code review (human decision 2026-11-22, "Cobrarlo"): the earlier rule skipped the buckets for every marker POST and let the ones no gate answered continue, so adding the marker to a form-encoded `POST /login` turned off a brute-force bucket on a router with a captcha and no AppSec, and a `bypassCaptcha` path got no bucket at all. Checking the policy and `match.BypassCaptchaName` before `HasChallengeMarker` also stops the up-to-64 KiB body peek on every POST of a router whose policy has no captcha answer. Amended in implement (conductor decision, option (a) of the explore question "Who validates the challenge-form POST of a captcha bucket on a router that does not subscribe to AppSec?"): a plain continue let the form reach the application unvalidated on a router without AppSec, so a captcha bucket could never be solved there (measured on real Traefik). It mirrors `answerAppSec`'s `isCaptchaFormAnswer` → `serveAppsecCaptchaGate`. The header and origin have no bucket because no bucket answered; `headerThirdField` gives `ratelimit` a third field only for an origin under `plugin:ratelimit:`; (c) `gateCleared` = `usableCaptcha().Check(req)`, computed once and only when the policy has a `captcha` bucket; (d) `Charge(ctx, client, b.name, req, ip, gateCleared)` under the 250ms step budget; (e) INFO per exceeded `log` bucket (unchanged); (f) `Err` → failure action; (g) ratelimit bucket → `denyRateLimit` (renamed for the action: the `ratelimit` answer); (h) captcha bucket → decision 8; (i) else continue. The counter key keeps `b.name`, the subscribing middleware (B-3).

7. **Verdict shape and walk.** `Verdict` gains a captcha bucket field beside the ratelimit bucket (renamed from `DenyBucket`), both with their `RetryAfter`. The walk keeps the first captcha bucket over its limit and goes on; a `ratelimit` bucket over its limit returns at once; a counter error returns at once and the caller applies the failure action even when a captcha bucket was kept. A skipped bucket — missing key value or, for a `captcha` bucket, `gateCleared` — is not charged, cannot answer, and its `final` does not apply (one meaning of "skipped"). `ActionDeny` becomes `ActionRateLimit = "ratelimit"` (default) and `ActionCaptcha = "captcha"` joins; `deny` fails compile with the accepted values.

8. **Captcha bucket answer.** `bypassesCaptcha` matched, or `usableCaptcha()` nil → `denyRateLimit` for that bucket (`rateLimitStatusCode`, `Retry-After`, `ban:ratelimit:<bucket>`, drop `ban`), plus the logging of decision 9. Otherwise `handleCaptchaKindServeHTTP(rw, req, ReasonRateLimit, headerReasonRateLimit, lapi.OriginPluginRateLimit(bucket))`: the formatter already adds the bucket as third field for reason `ratelimit`, so the header is `captcha:ratelimit:<bucket>`, and the challenge page records drop `captcha`. `warnCaptchaSuperseded` stays on the `ratelimit` answer only (a captcha answer serves a captcha, so a captcha rule did not lose).

9. **Logging of rate-limit captcha downgrades.** A bind hook on the rate-limit binding: when a non-nil Client whose policy has a `captcha` bucket or failure action `captcha` binds on a router with `Subscriptions.Captcha` false, ERROR `crowdsec bouncer rate limit captcha unavailable` (`reason` `unsubscribed`, `traefikName`, `instanceName`) once per bind transition — not on the request path. At request time, when the router subscribes to a captcha that is not usable and a rate-limit captcha answer downgrades: `logger.Debounced` ERROR, same message, `reason` `unusable`, 5s (the ModSec `MsgUnavailable` precedent). Every downgraded request: DEBUG. Owner loss (added after round-2 code review, human decision 2026-11-22, "WARN al desconectarse"): the rate-limit binding's unbind hook logs WARN `crowdsec bouncer rate limit owner unavailable` (`traefikName`, `instanceName`) once per move to no Client, and its bind hook logs INFO `crowdsec bouncer rate limit owner available` (`traefikName`, `instanceName`, `incarnation`) on the bind that ends that WARN, so a removed owner or a mistyped `rateLimitInstanceName` no longer turns the limit off with only a TRACE line. Requests still pass uncharged. Under Yaegi a subscriber that starts before its owner gets the typed nil from `Watch` and logs one WARN, then one INFO at the first bind; compiled Go skips that first delivery and logs neither. The failure-action `captcha` follows the same helper: when no usable captcha, it writes the existing `ban:captcha-downgrade` itself instead of reaching `handleCaptchaKindServeHTTP`'s per-request WARN branch. Reason: with the startup check gone (decision 10) that WARN would fire on every request of a Redis outage, which `core_plugin_ratelimit_client` forbids. The other legs' WARN is untouched.

10. **Validation.** `validateRateLimit` keeps running only when `rateLimitEnabled` (the owner) and drops `captchaInstanceNameReadyAfterOwnerFill` for `rateLimitFailureAction`; `compileBucketAction` accepts `ratelimit | captcha | log`. `validateOpenVsSubscribe` gains the rate-limit row: a leftover `rateLimitInstanceName` with neither `bouncerEnabled` nor `rateLimitEnabled` fails (E2); leftover owner-read `rateLimit*` keys on a subscriber are ignored. New field `RateLimitInstanceName` (json `rateLimitInstanceName`, default empty, alphabetical position).

11. **Metrics.** `plugin:ratelimit:<bucket>` with `ban` (ratelimit answer, downgraded or bypassed captcha bucket) or `captcha` (challenge page, recorded by the existing captcha writer). One origin without a bucket, added in implement with decision 6(b'): `plugin:ratelimit` with `captcha` when the captcha gate answers a challenge-form POST (the existing captcha writer records it before validating, as for the AppSec form answer). A cleared gate, a captcha-traffic skip, and an unpublished Client are not drops; a marker POST no gate answers is charged and counts as any other request (decision 6(b')).

12. **Proof that group 1 preserves behaviour.** On the extraction commit alone: `go test ./...`; the root Yaegi test in the GOPATH layout CI uses (`yaegi test .` from the module checkout does not find sources); a `pkg/yaegitest` program over the real binding and descriptor shapes; a new Go test that pins, for each of the four legs, the `crowdsec bouncer bound|unbound` attrs (`traefikName`, `leg`, `instanceName`, `incarnation`) across subscribe-before-publish, publish, replace, and clear, and the claim rollback order (taken name on each leg clears exactly the earlier enabled legs, one ERROR `crowdsec instance name taken`); local Pester `instance_severance`, `captcha`, `bypass_captcha`, `modsec`, `appsec`, `waf_dual`, `failure_action`. Existing tests change only where they read removed per-leg fields or call `bouncer.New` with four booleans, mechanically. The new trace test pins today's code (a replace logs unbound for the old incarnation, then bound for the new one), not the instance-slots scenario text that says otherwise (Risks).

13. **Test bar for groups 2–4.** Unit: `pkg/ratelimit` (key covers policy, not instance name; `Charge` precedence, captcha skip under `gateCleared`, `final` on a skipped bucket, error after a kept captcha bucket, `deny` rejected), `pkg/configuration` (owner-only validation, E2 row, captcha failure action passes), `pkg/bouncer` (unpublished passthrough, captcha challenge / bypass / no-captcha answers, captcha traffic skip, gate-cleared skip, bind ERROR once, debounced ERROR, no WARN, drops), root (`New` fill, publish, subscribe, rollback, `ClearPublisher` on flag drop, policy edit opens a new Client and keeps Redis counts with a fake or real counter). Real Redis: existing `realredis` tests stay. Real stack: decisions in the `build_e2e_pester_crowdsec-stack` delta.

## Risks / Trade-offs

- [A client that always posts the challenge marker to a router whose captcha gate answers it for the rate limit, or only fetches widget assets, is never charged, and each such marker POST costs a provider siteverify call.] → Human decision 5; recorded as `knowledge/debt/2026-11-21-rate-limit-captcha-marker-flood.md`.
- [A client that solved one captcha is exempt from `captcha` buckets for `captchaGracePeriodSeconds` (default 86400s).] → Human decision 4; README tells operators to stack a `ratelimit` bucket on the same key; nothing enforces it.
- [A subscriber passes everything while its owner is absent (fail open).] → Human decision on unpublished owner; one WARN on the loss and one INFO on the return show it (decision 9); a fail-closed subscriber key is not asked.
- [Any owner policy edit starts a new incarnation; a bucket rename restarts that bucket from zero.] → Counters live in Redis by subscriber and bucket name, so edits that keep names keep counts; README says so.
- [The trace keeps the previous incarnation string, not the pointer; two Clients that print the same `%p` would skip one TRACE line.] → Incarnations are `%p` of live Clients; a reused address needs the old one collected first; the bound value itself is unaffected.
- [The live instance-slots scenario "Replace A by B logs two bound lines … without an unbound between them" does not match the code, which logs unbound for A first.] → Pre-existing; this change does not widen it; the new trace test pins the code; recorded in `devstate` `issues.md` for a spec fix.
- [PR size: round-1 leg, refactor of four shipped legs, shared leg, bucket actions.] → Task group 1 is its own commit with its own proof; later groups are separate commits.

## Migration Plan

Unreleased on `master`. A round-1 configuration (one middleware with `rateLimitEnabled` + `bouncerEnabled`, no instance name) keeps working: the owner fills its name, publishes, subscribes to itself, and keeps the Redis keys `rl:<its name>:…`. `action: deny` must become `action: ratelimit` (or be omitted). Rollback is the previous plugin version; Redis keys keep their shape, so counts survive either way.
