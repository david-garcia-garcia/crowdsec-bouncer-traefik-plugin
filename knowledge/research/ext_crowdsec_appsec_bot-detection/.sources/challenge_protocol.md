Bot detection extends WAF/bouncer protocol with action `challenge` beside `allow`, `ban`, `captcha`. A challenge is a complete HTTP response (status, body, headers, cookies) generated by AppSec and relayed to the browser unchanged.

When challenging, AppSec answers the bouncer with HTTP 403 (usual blocked status) and JSON:

```
action: "challenge"
http_status: 200
user_body_content: "<!DOCTYPE html>..."
user_headers: map of header name → list of strings (Content-Type, Cache-Control, Content-Security-Policy)
user_cookies: list of Set-Cookie strings, e.g. "__crowdsec_challenge=...; Path=/; HttpOnly; SameSite=Lax"
```

http_status is the browser status, not the 403 the bouncer received. Official default if absent or zero: 200. Not always 200: GrantChallengeCookie() answers 307 plus Location in user_headers.

Internal paths (same 403 + action challenge + http_status 200 envelope):
- GET /crowdsec-internal/challenge/fpscanner.js
- GET /crowdsec-internal/challenge/pow-worker.js
- POST /crowdsec-internal/challenge/submit

Submit bodies: {"status":"ok"} (cookie in user_cookies), {"status":"failed"} (no cookie), {"status":"rejected"} (RejectSubmission, no cookie). Solved challenge is not allow on that hop.

Bouncer must: forward /crowdsec-internal/challenge/* unmodified, never to origin; return http_status not 403; set every user_headers (replace same name); emit each user_cookies as its own Set-Cookie; forward POST body; send real client IP in X-Crowdsec-Appsec-Ip; fail closed to ban if challenge cannot be served; only serve AppSec-issued challenge (LAPI challenge decision has no body).

Failure table: 200 allow; 403 challenge with body serve; 403 challenge empty body ban; 403 other action apply it; 403 empty/invalid JSON ban; 401/500/unexpected → APPSEC_FAILURE_ACTION.

Restrictiveness: allow < unknown < captcha < challenge < ban.
